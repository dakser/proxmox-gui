# Plan v0.1.1 (correcciones) y v0.2.0 (mejoras)

Origen: laboratorio en PVE anidado (`prox-t1`, PVE 9.2.2) con la release `v0.1.0`, 2026-11-01. Lo que sigue es un inventario
de lo que se observó de verdad, no de lo que se esperaba. Cada punto lleva su evidencia, su causa (cuando se conoce en el
código), el criterio de aceptación y la prueba que lo demuestra.

Reglas que no cambian (ver `CLAUDE.md`): ninguna escritura a Proxmox espera en la petición HTTP (UPID + job), tokens de API
con privilegios separados por equipo, el token nunca llega al navegador, nada de `.planning/*` a mano, commits pequeños y
atómicos. **Ningún cambio de este plan puede debilitar un control del endurecimiento** (firma de releases, usuarios
separados, sandbox de systemd, CSP, política de destinos, límite de intentos del setup). Si un punto lo exigiera, se para y
se pregunta.

Estado de partida: `master` con `v0.1.0` firmada y publicada. El job `scans` del CI está **en rojo** (ver L-00).

## 2. Mejoras: v0.2.0 (PRs separados)

| ID | Mejora | Notas de diseño |
|---|---|---|
| M-01 | El admin decide por usuario o equipo si puede crear **VM, LXC o ambas** | Se comprueba **en la API**, no solo ocultando botones. Auditoría del cambio |
| M-02 | El admin decide si un usuario puede **crear API tokens** | Al quitarlo, sus tokens existentes se **revocan** en el acto (decisión de Roberto), con entrada de auditoría. Reutilizar la revocación de `delete_user` |
| M-03 | Las etiquetas "VM" y "LXC" pasan a **VM-T1** y **VM-T2**, editables por el admin en Settings | Solo textos de la interfaz, iguales para todos y **sin traducir**. API, auditoría y documentación siguen con `vm`/`lxc` |
| M-04 | **Idiomas**: inglés y español, elegible por usuario en Profile | Guardado en la cuenta; por defecto, el del navegador o el que fije el admin. Archivos de idioma ampliables. La API devuelve **códigos de error** y la UI los traduce (esto también arregla varios mensajes engañosos) |
| M-05 | **Instalación independiente**: dentro de un LXC, VM o bare metal, además del modo actual | `install.sh` actual pasa a envolver un modo interno que corre en un Debian existente. Replantear el updater con root, la verificación de firma y la puerta SSH (hoy usan `pct exec`). Fuera de un CT sin privilegios, el sandbox de systemd es la defensa principal: volver a medir `systemd-analyze security` y probar |
| M-06 | **Backups por equipo**: el admin los habilita o deshabilita y elige el almacenamiento de cada equipo | Hoy es una designación por clúster. Decidir cómo se concede el permiso sobre el almacenamiento elegido |
| M-07 | Asistente con **listas**: plantillas del clúster, y nodo y almacenamiento rellenados según lo permitido por el admin | Hoy son campos de texto con ejemplos (`pve1`, `ubuntu-24.04...`) |
| M-08 | El admin decide si el usuario puede editar las **opciones del contenedor** (unprivileged, nesting, keyctl, fuse), ocultas por defecto | Dejar el perfil seguro por defecto reduce superficie |
